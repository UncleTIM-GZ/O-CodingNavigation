> 增订版本：v1.2 · 2026-06 · 对应 O'CodingNavigator SOP 0.3.0（artifact_logic_backbone）

## 原则｜先把逻辑主干接好线，再写代码

先设计「计算 · 决策图」，再实现。

### 为什么

AI Coding 里有一类最隐蔽的"假完成"：文档结构很齐全——模块名很多、指标很多、公式也很多——但真正运行时没人说得清：

- 先算什么、后算什么；
- 哪个公式服务哪个判断；
- 哪个分数进入下一层、哪个分数只做解释；
- 哪个信号能推动功能触发、哪个信号只能作为提示。

也就是说：**系统的"逻辑主干"在设计阶段从没被文档明确过**。它散落在多份文档的散文里、藏在每个人的脑子里。于是实施时不断漂移——越往后越乱，公式互相引用却对不上，分数定义了却没人消费，"信号"说会触发功能却没说触发哪个。

前面的设计层文档（信息架构、数据模型、接口契约）解决的是"系统有哪些东西、长什么样"；它们**不回答"这些东西按什么顺序、以什么角色连起来"**。这一层缺口，就是逻辑主干。

### 做法

在进入闭环层（写代码）之前，产出一份 **逻辑主干（Logic Backbone）文档**，把系统的计算/决策语义建成一张**有类型、有角色的有向图**（DAG + DMN 决策分层）：

**节点（每个都要标注 kind 与 role）**

- kind：`input`（输入/指标）· `formula`（公式）· `score`（分数）· `judgment`（判断/决策）· `signal`（信号）
- role：`input`（源）· `intermediate`（中间，要被下游消费）· `terminal_explanatory`（终点，只用于解释）· `trigger`（触发，驱动功能）· `hint`（提示，只告知不驱动）

**边（上游 → 下游，语义化，正好对应四个痛点）**

| 边 | 语义 | 回答的问题 |
|---|---|---|
| `feeds` | A 喂给 B（数据/分数依赖，构成算序 DAG） | 先算什么后算什么 |
| `serves` | 公式 → 判断 | 哪个公式服务哪个判断 |
| `feeds` | 分数 → 下游节点 | 哪个分数进入下一层 |
| `triggers` | 信号 → 功能/动作 | 哪个信号推动功能触发 |
| `explains` | 终点/提示 → 被解释对象（不驱动） | 哪个分数/信号只做解释、只作提示 |

**逻辑主干文档必须显式回答的四件事**（缺一不可）：执行顺序、公式归属、分数分层、信号作用级别。

### 怎样算"接好线"——可机器校验

逻辑主干不是写一段叙事就算完。它应当是单一事实源，并且**可被机器校验**。判定"未接线"的硬缺陷有六类，命中任一即不通过：

1. **缺角色**：节点没有合法 role。
2. **重复节点**：同一节点 id 出现多次。
3. **悬空引用**：边指向了未定义的节点。
4. **依赖环**：驱动子图（feeds/serves/triggers）里存在环。
5. **孤儿节点**：input/intermediate 节点没有任何下游消费它（只指向未定义节点也算孤儿）。
6. **未绑定触发**：role=trigger 的节点没有 triggers 边指向已定义目标。

> 在 O'CodingNavigator 里，这一原则已产品化为 SOP 0.3.0 的 `artifact_logic_backbone`：`ocn check` 对以上六类缺陷返回 blocked（退出码 2），逐条点名；通过后把规范化的图写入 `.ocoding/logic-graph.json`，并由 `ocn brief` 注入"执行顺序 + 触发清单"摘要，使 BUILD 阶段不再漂移。

### 范式参考（这是被验证过的老问题）

把隐式的图显式化、当成单一事实源、用自动校验防漂移——这在软件工程里有成熟先例：

- **dbt**：用 `ref()` 显式声明依赖 → 编译出 DAG → 有环/悬空引用直接 build 失败。
- **DMN（决策模型与标记法）**：决策需求图把"决策 ↔ 子决策 ↔ 输入数据"分层显式。
- **Event Modeling / CQRS**：区分能改变状态的 command（触发）与只供查看的 read model（提示）。
- **架构适应度函数**：把约束写成自动化测试，在 CI 里跑，违反就红。

一句话：逻辑主干 = "给业务逻辑用的 dbt" + "DMN 的决策分层语义"，钉死在设计阶段。
