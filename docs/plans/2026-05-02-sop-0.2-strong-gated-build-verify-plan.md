## 1. Goal｜目标

**Upgrade OCN from a Discovery-to-Plan gate engine into a Strong-Gated Verified Build Engine.**

That means SOP 0.2.0 closes the development SOP mainline end-to-end: every step from `00-project-brief.md` through `18-final-build-verdict.md` must have a stable `stepId`, an `artifactPath`, a bundled template, declared `requiredSections`, gate-runner enforcement, test coverage, an example fixture, and user-doc surfacing. After 0.2.0, an OCN-managed project that reaches a green `ocn advance` chain will have produced not just plans but also runnable code evidence and verification evidence — the discipline OCN sells (CLAUDE.md §1) extends past the document layer for the first time.

中文要点：把 OCN 从"只能强门禁 Discovery → Plan 的文档引擎"升级为"Plan → Build → Verify 全链路都有强门禁的开发 SOP 引擎"。每一个 00–18 的 step 都必须满足 stepId / artifactPath / template / requiredSections / gate / 测试 / examples / 文档八件套；0.2.0 之后，绿色 `ocn advance` 链能给出既有计划证据、也有代码证据、也有验证证据的工程产物。

## 2. Current gap｜现状缺口

Anchored to `src/sops/default-ai-coding-sop/0.1.0/data.ts` and the PDF-vs-shipped audit (§5–§7):

- **`00–09` required-section gates are looser than the PDF.** `02-prd.md` gates 5 of 14 PDF fields, `04-technical-architecture.md` gates 5 of 12 PDF sections, `01-scope.md` gates 4 of 9, `03-acceptance-criteria.md` gates 3 of 11.
- **`05–09` are file-existence-only gates.** `step_information_architecture` / `step_data_model` / `step_api_contract` / `step_test_strategy` / `step_mvp_plan` have an `artifactPath` but no entry in `REQUIRED_SECTIONS_BY_STEP`. `ocn check` passes if the file exists, regardless of content.
- **BUILD has no wired steps.** `STEPS_BY_STATE.state_build = []`. There is no `stepId` for dev log, research log, real-data wiring, configuration externalisation, reproducibility evidence, or rollback plan validation.
- **VERIFY has no wired steps.** `STEPS_BY_STATE.state_verify = []`. There is no `stepId` for validation report, debug report, baseline tracking, or final build verdict.
- **No code evidence is gated.** There is no required step that proves "real-data wiring exists", "configuration is externalised", "the repository can be reproduced", or "a rollback procedure was actually written down".
- **No verification evidence is gated.** There is no required step that proves the validation report was written, the debug report was filed, or that a final acceptance verdict was rendered against the AC document.
- **No acceptance-mapping evidence is gated.** `03-acceptance-criteria.md` is gated at SPEC time, but nothing later in the chain enforces "every AC has a verification result" — verification stops being machine-checkable the moment SPEC closes.

## 7. Gate rules｜门禁规则

1. **Every wired step is gated by required sections.** No file-existence-only gates for `05–18`. The historical "artifact-only" path (data.ts:263 comment) is removed for those steps; if a step has an artifact, it has required sections too.
2. **Required-section matching uses canonical + bilingual alias matching** (same engine as `00–04` today via `RequiredSectionDef`). Templates include the canonical heading text so a freshly-created template self-passes `ocn check`.
3. **`ocn advance` runs `ocn gate` first**, identical to 0.1.0 behaviour. There is no bypass; only documented `override` with a Decision Log reason. New step ids do not change this contract.
4. **`obligation_audit_trail` continues** to fire on every push event (`safeAudit()`), including all new BUILD / VERIFY transitions.
5. **`obligation_baseline_tracking` and `obligation_uncertainty_policy`** remain cross-cutting reminders rather than gates in 0.2.0; they are surfaced by `ocn brief` during BUILD / VERIFY but do not block `ocn advance`. Promoting them to wired steps is reserved for SHIP / REFLECT in a later SOP version.
6. **Snapshot drift detection** (`detect-version` / `snapshotDriftDetected`) continues to flag projects whose `.ocoding/sop.yaml` was generated by 0.1.0; the new 0.2.0 profile inherits the same drift model and a `0.1.0 → 0.2.0` upgrade is detected as `snapshot_legacy`.
7. **Terminal step in 0.2.0 is `state_verify / step_final_build_verdict`.** `state_ship` and `state_reflect` keep `steps: []` (explicit stubs), so `ocn advance` at the terminal step continues to report "no further step in the active SOP profile" — the same behaviour the example smoke validates today (`examples/discovery-to-plan/scripts/smoke.sh`).

## 8. Implementation PR sequence｜实施 PR 顺序

Each PR is a separate DEC-bound action. None of them are authorised by the present DEC-023 / this plan; each requires its own approval.

1. **PR 1 — Profile data and rendered snapshots.**
   - New directory `src/sops/default-ai-coding-sop/0.2.0/` parallel to `0.1.0/`.
   - `data.ts`: add the 9 new step defs to `STEPS_BY_STATE`, register the 19 `requiredSections` entries (5.1–6.9), bump `PROFILE_VERSION`.
   - `render.ts`, `sop.ts`, `gates.ts`, `artifacts.ts`, `config.ts`: regenerate from data.
   - `README.md` + `CHANGELOG.md` for the new profile.
   - SOP loader (`src/core/sop/loader.ts`) chooses the active profile (default flip to `0.2.0` decided at PR 1 time per §9 below).

## 9. Migration strategy｜迁移策略

- **Existing 0.1.0 projects remain readable.** The 0.1.0 profile directory stays in the repo. SOP loader continues to recognise `version: "0.1.0"` snapshots; only the *active* profile compiled into the binary changes.
- **Fresh `ocn init` uses 0.2.0** only after the profile-data PR (PR 1) merges. Until that merge, `ocn init` keeps writing 0.1.0 snapshots.
- **Legacy projects detect snapshot drift.** A 0.1.0-locked project running an OCN binary that ships 0.2.0 will see `detectSopVersion` report `diffDetected: true` and `snapshotDriftReason: "snapshot_legacy"`. The user is told via `ocn brief` / `navigator.detect_sop_version`, but no auto-rewrite happens.
- **No auto-rewrite of `.ocoding/sop.yaml` without explicit user action.** Migration from 0.1.0 → 0.2.0 stays manual (e.g. a future `ocn sop upgrade` command); 0.2.0 ships without that command, in line with CLAUDE.md §10's "advance is human-only" stance.
- **Decide whether `ocn init` default flips to 0.2.0** at the start of PR 1: either flip immediately (cleanest user story for new projects, but means 0.1.0 install can no longer be requested without a flag) or land 0.2.0 as opt-in (`ocn init --sop default-ai-coding-sop@0.2.0`) for one beta cycle, then flip in beta.2. Default recommendation: **flip immediately on PR 1** because beta lane is by definition non-stable; alternative is recorded in this plan so the PR 1 author has both options on the table.

## 11. Risks｜风险

1. **Template drift.** 19 templates × bilingual canonical headings is a lot of surface; a single typo in a template header breaks the gate. Mitigation: PR 2 includes a "template self-passes its own gate" assertion fixture per step.
2. **Required-section over-fit.** Tightening `02-prd.md` from 5 → 12 sections risks blocking projects that had a passing PRD under 0.1.0. Mitigation: rely on snapshot-drift detection — 0.1.0-locked projects keep their 0.1.0 gates; only fresh `ocn init` projects (or projects that explicitly upgrade) see 0.2.0 gates.
3. **BUILD / VERIFY artifacts becoming "checkbox docs".** A user could write a 1-line "Findings: TBD" under each section to pass the gate. Mitigation: 0.2.0 still gates on section presence, not content quality; quality is the user's responsibility. This is consistent with CLAUDE.md §10 / scope.md "minimum gating, not maximum requirements". A future `obligation_quality_review` can lift this in 0.3.x.
4. **Snapshot file diff explosion.** `.ocoding/sop.yaml` for 0.2.0 projects contains 19 step ids vs 10 today. Diff churn in test fixtures and audit logs. Mitigation: rendered output is deterministic; fixture updates are mechanical.
5. **MCP host token cost.** `navigator.brief` output grows because the next-step list is longer. Mitigation: the brief renderer already truncates; if the post-0.2.0 brief exceeds a reasonable token budget, PR 6 trims to "current state's wired steps only".
6. **Test-runtime regression.** Adding 9 step types × multiple fixtures could push CI runtime past the current ~3.7s vitest budget. Mitigation: parallelise fixtures inside vitest projects; the gate engine itself is pure I/O-light.
7. **Dogfood risk if executed before merge of PR 1–5.** Running real OCN-managed dogfood against a partial 0.2.0 (e.g. data merged but templates not yet shipped) would produce confusing errors. Mitigation: hold dogfood until **at least PR 1–5 merge and the plan-to-verify smoke is green** (recommendation §12).
