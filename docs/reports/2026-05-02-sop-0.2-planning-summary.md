## 1. Why this plan exists｜本规划存在的原因

OCN v0.1.0-beta.0 ships a strong-gated DISCOVERY → PLAN engine. After `state_plan / step_mvp_plan` the gate runner has nothing else to enforce: `STEPS_BY_STATE.state_build`, `state_verify`, `state_ship`, `state_reflect` are intentionally empty in `src/sops/default-ai-coding-sop/0.1.0/data.ts` (lines 98–101). A user reaching the terminal step today gets a green `ocn advance` reply that says "no further step in the active SOP profile", and from that moment on OCN's discipline is purely advisory — `ocn brief` reminders, cross-cutting obligations in CLAUDE.md §5, and `safeAudit()` push events.

The PDF SOP (`docs/AI Coding 最佳实践开发 SOP完整版.pdf`) defines a much longer mainline: real-data wiring (§11), configuration externalisation (§12), reproducibility (§13), rollback path (§14), small-sample validation (§15), problem layering (§16), input-vs-logic fixes (§17), baseline (§18), acceptance verdict (§19), and so on through §29. The PDF-vs-shipped audit (§5–§7) confirms that for documents `10–25` OCN today reserves the file numbers but does not promote them to wired `step_*` ids with required-section gates.

This plan exists because the user has explicitly asked for the SOP mainline to close (Plan → Build → Verify) before dogfood begins. SOP 0.2.0 is the version that makes that closure happen.

---

## 2. User concern｜用户关切

The user's stated concern is two-pronged:

1. **OCN must not stop at the document layer.** Selling "discipline" while only enforcing planning artifacts means a project can produce a beautiful PRD / AC / architecture stack and still ship code with no real-data wiring, no rollback plan, no validation report, no debug trail — exactly the failure modes the PDF SOP exists to prevent.
2. **Dogfood must run against an end-to-end SOP, not a half SOP.** Starting dogfood on a SOP that gates only `00–09` would either (a) produce dogfood findings that say "BUILD / VERIFY have nothing to test", which is useless feedback, or (b) tempt the dogfood project to invent ad-hoc post-PLAN process, which contaminates the eventual 0.2.0 design with implicit decisions never captured in DEC entries.

中文要点：用户希望 OCN 卖的"纪律"不要在 PLAN 之后就消失，并且要求在用一个完整的 Plan → Build → Verify SOP 自我吃狗粮（dogfood）之前先把这条主链路补完，避免 dogfood 反过来污染 0.2.0 的设计。

---

## 3. Why PLAN-only is insufficient｜为什么只有 PLAN 是不够的

- **No code evidence.** v0.1.0-beta.0 has no `step_real_data_wiring`, no `step_reproducibility`. A project can pass `ocn check` everywhere and still have hard-coded credentials, no lockfile, and no clean-machine setup notes.
- **No rollback evidence.** `obligation_rollback_awareness` (CLAUDE.md §5) is a reminder, not a gate; nothing prevents `ocn advance` past PLAN with the rollback plan never written.
- **No validation evidence.** Verify state has zero wired steps. Acceptance criteria written in `03-acceptance-criteria.md` at SPEC time have no enforced counterpart in VERIFY (no "every AC has a result" check).
- **No debug evidence.** No `step_debug_report`, no `step_dev_log` in the gate chain. The PDF's "fix input first, then fix logic" discipline (§17) lives only as cross-cutting prose.
- **No final verdict.** No `step_final_build_verdict`. There is no machine-readable point at which a project says "the build is acceptable to ship" inside the SOP itself; today this is asserted out-of-band in PR descriptions, release notes, or DEC entries.

Each gap is exactly one of the false-completion modes that `docs/00-project-brief.md` lists as the reason OCN exists.

---

## 4. Why `0–18` is selected instead of full `0–25`｜为什么选 0–18 而不是完整的 0–25

The plan's scope choice was made by elimination among the four options recorded in DEC-023:

- Option A (dogfood 0.1.0 first) — rejected because dogfood without BUILD / VERIFY is not a fair test of the SOP.
- Option B (only tighten 0–9) — rejected because it leaves the post-PLAN void intact and changes nothing about whether OCN can gate code or verification.
- Option C (full 0–25 in one bump) — rejected because SHIP / REFLECT (`19-dev-log` cross-cutting + `20-baseline` + `21-observability` + `22-audit-trail` + `23-evolution-report` + `24-ai-governance` + `25-uncertainty-policy`) span post-delivery, governance, and long-term evidence flows that are best validated against an already-working dev loop. Bundling them with the dev-loop closure risks instability across all eight states at once.
- Option D (`0–18`, dev loop only) — accepted because it closes the development SOP mainline (Plan → Build → Verify) and keeps SHIP / REFLECT as a separately-scoped future bump.

The 0–18 cut also lines up cleanly with the audit's §5 table: docs `19–25` are exactly the ones backed today by cross-cutting obligations that should not become hard `ocn advance` gates until SHIP / REFLECT have their own dedicated planning cycle.

## 5. What is not authorised by this DEC｜本 DEC 不授权的事情

DEC-023 authorises **planning only**. The following actions are explicitly out of scope and require their own DEC:

- No `npm publish` of any version.
- No `npm dist-tag` change. The `latest` tag stays on `0.1.0-alpha.0` per DEC-020 / DEC-021.
- No GA promotion. SOP 0.2.0 will publish (if it publishes at all) under the `beta` lane via a separate DEC modelled on DEC-021 / DEC-022.
- No `git tag` creation. No GitHub Release. The DEC-022 release-marker policy applies to specific versions; it does not pre-authorise future tags.
- No source / test / package / workflow change in the present PR. This PR is docs-only (DEC entry + plan + this report). Implementation lives in PR 1–6 of the plan, each its own DEC-bound action.
- No Cursor / Cline support claim. DEC-019 host-support boundary stands.
- No dogfood start. The recommendation in the plan §12 is "do not start dogfood until at least PR 1–5 are merged and the plan-to-verify smoke passes".

## 7. PDF read fallback｜PDF 读取回退说明

The PDF `docs/AI Coding 最佳实践开发 SOP完整版.pdf` could not be read directly in the planning session that authored DEC-023 / the plan / this summary, because the local environment lacks `pdftoppm` (poppler-utils) which the file-reader tool requires for PDF rendering. To stay accurate without inventing PDF content, the planning session fell back to:

- `docs/reports/2026-05-02-pdf-vs-shipped-sop-consistency-audit.md` — the prior PDF-vs-shipped audit, which already enumerated PDF chapters §1–§29, document numbers `00–25`, and per-document recommended fields (audit §3, §5, §6).
- `src/sops/default-ai-coding-sop/0.1.0/data.ts` — the canonical shipped SOP profile, which provides the existing stable ids and required-section structures the new 0.2.0 entries must extend.
- `CLAUDE.md` §4 / §5 / §10 and `docs/01-scope.md` for the v1.0 scope boundary, hard rules on stable ids, and the cross-cutting obligations the plan must respect.

This fallback is consistent with CLAUDE.md §2's "If the doc disagrees with what you remember, the doc wins" — the audit report is itself a doc derived from the PDF and is the closest in-repo artifact to the PDF source. Any future PR that has direct PDF access should re-cross-check the section names in plan §5 / §6 against the PDF and amend via DEC-023's follow-up sequence if discrepancies are found.
